# Как выпустить релиз

Приложение раздаётся образом DMG мимо App Store, а обновления приходят через
Sparkle. Чтобы человек, который поставил Wai Dictation, получил новую версию,
должны сойтись три вещи: подписанный и нотаризованный образ, подпись
обновления и запись в ленте. Не сойдётся любая одна — обновление не приедет,
и починить это у уже установленного приложения будет нечем.

Всё делает `scripts/release.sh`. Ниже — что подготовить один раз, что делать
на каждый выпуск, как убедиться, что вышло именно то, и что делать, если
вышло плохое.

---

## Один раз, до первого релиза

Пять пунктов. Пока не сделаны все пять, релиз выпускать нельзя.

### 1. Ключ подписи обновлений

Sparkle поставит только тот образ, который подписан вашим ключом. Пара
создаётся один раз на все версии и на все приложения.

```bash
BIN=~/Library/Developer/Xcode/DerivedData/WaiDictation-*/SourcePackages/artifacts/sparkle/Sparkle/bin

# Создать пару. Приватный ключ уедет в связку ключей login, публичный напечатается.
$BIN/generate_keys

# Выгрузить приватный ключ в файл — его читает скрипт релиза.
mkdir -p ~/.wai-dictation
$BIN/generate_keys -x ~/.wai-dictation/sparkle-key
chmod 600 ~/.wai-dictation/sparkle-key
```

`generate_keys -x` откажется писать поверх существующего файла — это
намеренно, чтобы нельзя было случайно затереть выгруженный ключ.

Приватный ключ не коммитьте никогда и не кладите в репозиторий даже
временно. Держите его в связке ключей **и** в резервной копии за пределами
машины: потеряете — новые версии перестанут приезжать всем, кто уже поставил
приложение. Завести второй ключ нельзя, старые копии о нём не знают.

Инструменты Sparkle (`generate_keys`, `sign_update`) приезжают вместе с
пакетом: Xcode распаковывает их в DerivedData при первой сборке. Отдельно
ставить ничего не нужно. Если путь другой — передайте его переменной
`SPARKLE_BIN`.

### 2. Публичный ключ в проекте

Возьмите публичный ключ и впишите его в `apps/macos/project.yml` как
`SUPublicEDKey` — там для него оставлена закомментированная строка:

```bash
$BIN/generate_keys -p      # печатает ровно одну строку: сам ключ в base64
```

```yaml
SUPublicEDKey: "<44 символа base64, ровно то, что напечатал generate_keys -p>"
```

Он публичный, его место в репозитории — приложение проверяет им подпись.

**Это должно быть сделано до самого первого релиза, а не после.** Без
`SUPublicEDKey` приложение отключает обновления совсем: `SparkleUpdater`
проверяет ключ сам и, не найдя его, показывает в настройках «Обновления
отключены: без него их нечем проверить». Собственная проверка Sparkle здесь
мягче — при HTTPS-адресе ленты и подписанном приложении она пропускает
отсутствие ключа и переходит на проверку одной лишь подписью Apple. Мы на это
не соглашаемся: обещание «обновления подписаны нашим ключом» иначе тихо
ослабло бы. Практический вывод один: версия, выпущенная без ключа в
`Info.plist`, не обновится никогда и ничем.

Ключ в `project.yml` обязан соответствовать **файлу** из пункта 1 — именно им
`release.sh` подписывает образ, а не тем, что лежит в связке ключей. Расхождение
связки и файла ничего не значит; расхождение файла и `project.yml` значит, что
обновление не установится ни у кого.

`release.sh` эту пару сверяет сам и останавливается на расхождении. Сверить
заранее, до сборки и без связки ключей, — тем же способом, каким это делает он:

```bash
swift - ~/.wai-dictation/sparkle-key <<'SWIFT'
import CryptoKit
import Foundation
let text = try String(contentsOfFile: CommandLine.arguments[1], encoding: .utf8)
let seed = Data(base64Encoded: text.trimmingCharacters(in: .whitespacesAndNewlines))!
print(try Curve25519.Signing.PrivateKey(rawRepresentation: seed)
    .publicKey.rawRepresentation.base64EncodedString())
SWIFT
grep SUPublicEDKey apps/macos/project.yml
```

Строки совпали — круг замкнут. Печатается только публичный ключ, приватный
никуда не попадает.

### 3. Сертификат и нотаризация

- Сертификат **Developer ID Application** в связке ключей.
- Team API key App Store Connect:
  - `~/.appstoreconnect/config.json`, mode `0600`;
  - `key_filepath`, `key_id`, `issuer_id`;
  - `.p8` в `~/.appstoreconnect/private_keys/`, mode `0600`.

Подготовить и проверить локальные credentials без вывода секретов:

```bash
./scripts/bootstrap-release-secrets.sh
```

Скрипт восстанавливает Sparkle key из 1Password. App Store Connect credentials
остаются file-based: скрипт проверяет config и при необходимости копирует
выбранный `.p8` в стандартный каталог. `release.sh` передаёт `notarytool`
`--key`, `--key-id` и `--issuer`. Сохранённый `NOTARY_PROFILE` поддерживается
только как явная альтернатива; смешивать его с API key запрещено.

Ненотаризованный образ Gatekeeper не пустит, и обновление превратится в
сломанное приложение у всех, кто его поставил.

### 4. Репозиторий и лента

- Репозиторий `mikwiseman/wai-dictation` опубликован. На него ссылаются и
  лента, и адреса образов, и запасной источник модели.
- **Settings → Pages → Source: Deploy from a branch → `main` / `/docs`**.
  Оттуда раздаётся `docs/appcast.xml`, и адрес совпадает с `SUFeedURL` из
  `project.yml`: `https://mikwiseman.github.io/wai-dictation/appcast.xml`.
  Рядом лежит `docs/.nojekyll`, чтобы файлы отдавались как есть.

### 5. Запасной источник моделей

Модели приложение берёт с Hugging Face, а если тот недоступен — из релизов на
GitHub. Моделей **две**, и у каждой свой манифест со своим `mirror`:

| Манифест | Тег зеркала | Файлов | Байт |
|---|---|---|---|
| `Resources/model-manifest.json` (распознавание) | `models-aed02740` | 21 | 483 105 645 |
| `Resources/vocabulary-manifest.json` (подсказчик терминов) | `models-accdafd8` | 16 | 102 803 869 |

Оба релиза выложены. Проверять надо не «есть ли релиз», а сходятся ли ассеты с
манифестом по именам и по байтам — иначе половина зеркала молча не работает:

```bash
python3 - <<'PY'
import json, subprocess
for tag, path in (
    ("models-aed02740", "Packages/LocalASR/Sources/LocalASR/Resources/model-manifest.json"),
    ("models-accdafd8", "Packages/LocalASR/Sources/LocalASR/Resources/vocabulary-manifest.json"),
):
    want = {f["path"].replace("/", "__"): f["byteCount"] for f in json.load(open(path))["files"]}
    rows = subprocess.run(
        ["gh", "release", "view", tag, "--json", "assets", "--jq", ".assets[]|[.name,.size]|@tsv"],
        capture_output=True, text=True).stdout.split()
    have = dict(zip(rows[0::2], map(int, rows[1::2]))) if rows else {}
    missing = [k for k in want if have.get(k) != want[k]]
    print(tag, "ок" if not missing and len(have) == len(want) else f"РАСХОЖДЕНИЕ: {missing[:5]}")
PY
```

Каждый файл — отдельный ассет. Имя ассета это путь файла, где `/` заменён на
`__` (`Encoder.mlmodelc/weights/weight.bin` →
`Encoder.mlmodelc__weights__weight.bin`). Ни архивов, ни вложенных папок:
приложение забирает файлы по одному и сверяет sha256 каждого.

Тег привязан к ревизии модели. Сменится ревизия в любом из двух манифестов —
понадобится новый релиз с новым тегом, старый удалять не нужно. Пропадёт
зеркало — упадёт Hugging Face, и новый пользователь не сможет поставить модель
вообще, то есть приложение для него не заработает.

## Проверить, что подпись обновлений вообще работает

Связка «подписать → проверить» — единственное место контура, где ошибка не
видна до тех пор, пока обновление не поедет к людям. Проверять её боевым
ключом не нужно и не стоит: он лежит в связке ключей и достаётся оттуда с
запросом доступа. Весь круг проходится одноразовым ключом, который к связке
ключей не имеет отношения.

**У `generate_keys` нет режима «создать пару в файл».** Все четыре режима
работают со связкой ключей: без аргументов — создаёт в ней, `-p` — читает из
неё, `-x` — выгружает из неё, `-f` — импортирует в неё. Обойти это можно
законно, потому что формат файла с приватным ключом описан самим Sparkle
(`generate_keys --help`, реализация — `common_cli/Secret.swift`): это
**base64 от 32-байтового seed ed25519**. Старый формат — 96 байт (64 байта
приватного ключа плюс 32 публичного) — тоже принимается, но новые ключи
хранятся как seed. Значит, одноразовую пару можно получить из 32 случайных
байт, ничего никуда не записывая.

```bash
cd "$(mktemp -d)"
BIN=~/Library/Developer/Xcode/DerivedData/WaiDictation-*/SourcePackages/artifacts/sparkle/Sparkle/bin

# Приватный ключ: 32 случайных байта в base64. Связка ключей не участвует.
openssl rand 32 | base64 > throwaway-key
chmod 600 throwaway-key

# Публичный ключ из него же — средствами системы, без сторонних библиотек.
cat > pub.swift <<'SWIFT'
import CryptoKit
import Foundation
let seed = Data(base64Encoded: try String(contentsOfFile: CommandLine.arguments[1], encoding: .utf8)
    .trimmingCharacters(in: .whitespacesAndNewlines))!
print(try Curve25519.Signing.PrivateKey(rawRepresentation: seed)
    .publicKey.rawRepresentation.base64EncodedString())
SWIFT
swift pub.swift throwaway-key
```

Дальше — круг на настоящем образе:

```bash
DMG=/путь/к/WaiDictation-0.1.0.dmg

SIG=$("$BIN"/sign_update -p --ed-key-file throwaway-key "$DMG")
echo "$SIG"                        # 88 символов base64
"$BIN"/sign_update --verify --ed-key-file throwaway-key "$DMG" "$SIG"
echo "код возврата: $?"            # 0 и ни строчки вывода — это успех
```

Тихий успех — единственный признак, что подпись сошлась: при удаче
`sign_update --verify` не печатает ничего. При неудаче печатает
`Error: failed to pass signing verification.` и возвращает 1.

Осталось убедиться, что тем же ключом её примет и само приложение. Публичный
ключ кладётся в **копию** бандла, боевую сборку трогать не надо:

```bash
cp -R "artifacts/build/WaiDictation.xcarchive/Products/Applications/Wai Dictation.app" ./test.app
/usr/libexec/PlistBuddy -c "Add :SUPublicEDKey string $(swift pub.swift throwaway-key)" \
  test.app/Contents/Info.plist
```

Проверка тем же способом, каким её делает Sparkle, — сверка подписи с
`SUPublicEDKey` из `Info.plist` бандла (`SUHost` → `SUPublicKeys` →
`ed25519_verify`). То же самое делает `Curve25519.Signing.PublicKey` из
CryptoKit: это один и тот же ed25519 из RFC 8032, и на одинаковых входах они
дают одинаковый ответ.

```bash
cat > verify.swift <<'SWIFT'
// Сходится ли подпись обновления с публичным ключом приложения.
// Ничего секретного не нужно: ключ из Info.plist, подпись из ленты.
//   swift verify.swift <публичный ключ> <файл> <подпись>
import CryptoKit
import Foundation
let a = CommandLine.arguments
guard a.count == 4,
      let raw = Data(base64Encoded: a[1]), raw.count == 32,
      let key = try? Curve25519.Signing.PublicKey(rawRepresentation: raw),
      let sig = Data(base64Encoded: a[3]), sig.count == 64,
      let data = try? Data(contentsOf: URL(fileURLWithPath: a[2]))
else { print("Не разобрал ключ, подпись или файл"); exit(2) }
if key.isValidSignature(sig, for: data) {
    print("Подпись сходится: это приложение примет это обновление.")
} else {
    print("ПОДПИСЬ НЕ СХОДИТСЯ. Обновление не установится ни у кого.")
    exit(1)
}
SWIFT

KEY=$(/usr/libexec/PlistBuddy -c "Print :SUPublicEDKey" test.app/Contents/Info.plist)
swift verify.swift "$KEY" "$DMG" "$SIG"
```

Круг замкнут, если проходят все пять проверок:

| Что подставили | Что должно получиться |
|---|---|
| свой ключ, своя подпись, свой образ | «Подпись сходится» |
| подпись, сделанная другим ключом | «ПОДПИСЬ НЕ СХОДИТСЯ» |
| своя подпись с испорченным битом | «ПОДПИСЬ НЕ СХОДИТСЯ» |
| свой ключ и подпись, но изменённый образ | «ПОДПИСЬ НЕ СХОДИТСЯ» |
| чужой публичный ключ в `Info.plist` | «ПОДПИСЬ НЕ СХОДИТСЯ» |

Если хоть одна подделка проходит — проверки нет, и дальше идти нельзя.

Мусор после репетиции: `rm -rf` временной папки. Одноразовый ключ нигде не
регистрируется, удаления из связки ключей не требует.

`verify.swift` из этого раздела стоит сохранить отдельно от временной папки —
он же нужен на каждом выпуске, в разделе «Проверить, что вышло». Ничего
секретного в него не попадает: на вход идут публичный ключ и подпись.

## Каждый релиз

### 1. Поднять версию

В `apps/macos/project.yml`:

- `MARKETING_VERSION` и `CFBundleShortVersionString` — то, что видит человек
  (`0.2.0`). Обе строки должны совпадать, скрипт это проверяет.
- `CURRENT_PROJECT_VERSION` — целое число, которое обязано **расти**. Именно
  его сравнивает Sparkle: версия с номером не больше опубликованного просто
  не приедет никому.

Бампу — отдельный коммит после самой работы: черновик «что нового» скрипт
собирает из заголовков коммитов после последнего тега.

### 2. Прогнать то, чего не проверяет CI

```bash
./scripts/check-network-surface.sh     # сеть только там, где обещано (доли секунды)
./scripts/test-zero-network.sh         # распознавание работает в песочнице без сети
./scripts/test-zero-network-trace.sh   # tracer: ноль DNS/connect/send без песочницы
```

Статический scan гоняет и CI; оба runtime-гейта — нет, и `release.sh` требует
именно все три. Двум последним нужна уже установленная модель — они проверяют
то, что происходит после загрузки. Без неё выйдет с кодом 69 и скажет об этом.
Прогон целиком —
**0,6 с** на M4 Pro с собранным `asr-bench` и до ~2,6 с, когда SwiftPM заново
разбирает манифест. Первый запуск в чистом дереве дольше на сборку самого
инструмента.

Это главное обещание продукта, и проверяется оно только здесь: в CI модели
нет и качать её туда не надо.

Живой путь — микрофон, голос, задержка — сюда не входит вовсе: он проверяется
владельцем через `./scripts/self-check.sh` и [manual-check.md](manual-check.md).
Перед релизом стоит прогнать оба: ни один автоматический гейт не скажет, что
диктовка работает на настоящем голосе.

### 3. Собрать, подписать, нотаризовать

```bash
SPARKLE_KEY_PATH=~/.wai-dictation/sparkle-key \
DEVELOPER_ID="Developer ID Application: Имя (TEAMID)" \
./scripts/release.sh
```

Что делает скрипт по порядку:

1. требует **чистое дерево, ветку `main`, `HEAD` = `origin/main` и зелёный
   завершённый прогон CI ровно на этом SHA** (через `gh`) — это самая первая
   проверка, до ключа и до сертификата. Отсюда правило: сначала запушить и
   дождаться CI, только потом запускать релиз;
2. требует файл с приватным ключом и сертификат;
3. сверяет `MARKETING_VERSION` и `CFBundleShortVersionString` в `project.yml`
   и требует описание изменений: если файла `docs/release-notes/<версия>.md`
   нет, набрасывает черновик из коммитов и останавливается;
4. проверяет сетевую поверхность;
5. требует `quality/live-benchmark-report.json` и сверяет его
   `scripts/validate-live-benchmark.py` — это гейт живого голоса, см.
   [quality/README.md](../quality/README.md);
6. гоняет тесты обоих пакетов **и тесты приложения** (`xcodebuild … test`);
7. гоняет оба runtime-гейта без сети — песочницу и tracer;
8. собирает, подписывает и нотаризует образ (`scripts/build-dmg.sh`);
9. прогоняет `scripts/smoke-installed-artifact.sh` по собранному бандлу:
   arm64-only, minOS 14.0, entitlement на микрофон, обязательные лицензии
   и манифесты внутри `Contents/Resources`;
10. убеждается, что в `Info.plist` есть `SUFeedURL` и `SUPublicEDKey`, версия
    совпадает с той, на которую написано описание, приложение подписано именно
    `Developer ID Application`, ticket пристеплен и Gatekeeper принимает образ;
11. требует `quality/release-evidence.json` — заполненную вручную матрицу
    [quality/manual-release-matrix.md](../quality/manual-release-matrix.md)
    ровно для этого SHA и этого sha256 образа — и сверяет её
    `scripts/validate-release-evidence.py`;
12. подписывает образ ключом EdDSA, проверяет подпись **и отдельно сверяет,
    что публичный ключ в `Info.plist` выведен из этого же приватного** —
    расхождение здесь означало бы зелёный релиз, который не установится ни у
    кого;
13. дописывает версию в `docs/appcast.xml` — свежая первой, старые ниже, не
    больше десяти.

Пункт 11 — единственный, который нельзя выполнить заранее: матрица
заполняется по **уже подписанному и нотаризованному** образу. Поэтому порядок
такой: первый запуск доходит до пункта 11 и останавливается; вы проверяете
образ руками, заполняете `quality/release-evidence.json` (файл в `.gitignore`,
шаблон — `quality/release-evidence-template.json`); второй запуск идёт без
пересборки и без повторной нотаризации:

```bash
SPARKLE_KEY_PATH=~/.wai-dictation/sparkle-key \
DEVELOPER_ID="Developer ID Application: Имя (TEAMID)" \
REUSE_VERIFIED_ARTIFACT=1 \
./scripts/release.sh
```

Первый запуск на новой версии всегда останавливается на черновике описания.
Это нормально: перепишите его человеческим языком (это увидят все, кому
предложат обновление) и запустите заново. Остановка стоит до сборки
намеренно — нотаризация идёт минуты, и упираться после неё в ненаписанный
текст обидно.

Сборка образа без нотаризации занимает около минуты. Нотаризация добавляет
несколько минут ожидания ответа Apple.

### 4. Разложить по местам

Скрипт печатает готовые команды. По сути их три:

```bash
gh release create v0.2.0 artifacts/dmg/WaiDictation-0.2.0.dmg \
  --title "0.2.0" --notes-file docs/release-notes/0.2.0.md

git add docs/appcast.xml docs/release-notes/0.2.0.md apps/macos/project.yml
git commit -m "release: 0.2.0" && git push
```

Порядок важен: сначала образ, потом лента. Ссылка в ленте ведёт на файл
релиза, и если ленту опубликовать первой, кто-то успеет получить обновление,
которого ещё нет.

## Проверить, что вышло

Прогоняется целиком, каждый раз. Первые четыре пункта — за минуту.

```bash
V=0.2.0

# 1. Лента живая и содержит новую версию.
curl -sSf https://mikwiseman.github.io/wai-dictation/appcast.xml | head -20

# 2. Образ лежит там, куда ведёт лента (ссылку взять из <enclosure url=…>).
curl -sSfI https://github.com/mikwiseman/wai-dictation/releases/download/v$V/WaiDictation-$V.dmg

# 3. Gatekeeper принимает образ — значит нотаризация доехала.
spctl -a -vv -t install artifacts/dmg/WaiDictation-$V.dmg

# 4. Подпись из ленты сходится с ключом из сборки.
#    Скрипт verify.swift — из раздела про подпись выше, ничего секретного не нужно.
KEY=$(/usr/libexec/PlistBuddy -c "Print :SUPublicEDKey" \
  "artifacts/build/WaiDictation.xcarchive/Products/Applications/Wai Dictation.app/Contents/Info.plist")
SIG=$(python3 -c "import sys,xml.etree.ElementTree as ET; \
  print(ET.parse('docs/appcast.xml').getroot().find('channel/item/enclosure') \
  .get('{http://www.andymatuschak.org/xml-namespaces/sparkle}edSignature'))")
swift verify.swift "$KEY" artifacts/dmg/WaiDictation-$V.dmg "$SIG"
```

Четвёртый пункт — тот самый, ради которого всё это. Он ловит и подпись не тем
ключом, и не тот ключ в сборке, и подменённый по дороге образ, и не требует
доступа к приватному ключу.

**И только потом — настоящая проверка.** Поставьте **предыдущую** версию,
включите в настройках «Проверять обновления автоматически», нажмите
«Проверить обновления…» и пройдите установку до конца. Подпись, лента и образ
сходятся только все вместе, и никакая отдельная проверка этого не заменяет.

Отдельно стоит один раз пройти путь нового человека: скачать образ по ссылке
из релиза (именно скачать — тогда на файле окажется карантин, как у всех),
смонтировать, перетащить в «Программы», запустить. Окно первого запуска
должно открыться само в первые доли секунды: приложение живёт в строке меню,
и если окно не появится, человек не увидит вообще ничего.

## Если релиз оказался плохим

У Sparkle нет отзыва: у кого обновление уже установилось, у того оно
установлено. Всё, что можно сделать, — остановить раздачу остальным и как
можно быстрее выпустить исправление.

**Сразу, в таком порядке:**

1. **Убрать запись из ленты.** Удалите `<item>` плохой версии из
   `docs/appcast.xml`, закоммитьте, запушьте. Через минуту-другую Pages
   раздаст новую ленту, и те, кто ещё не проверял обновления, ничего не
   получат. Это самое быстрое, что есть, и делать это надо первым.
2. **Только после этого — снять релиз.** `gh release delete v0.2.0` (или
   пометить черновиком). Если снять образ раньше, чем убрать запись из ленты,
   у тех, кто в этот момент нажал «Проверить обновления», загрузка упадёт с
   невнятной ошибкой вместо тишины.
3. **Не переиспользовать номер сборки.** Выпускайте исправление с новым,
   бо́льшим `CURRENT_PROJECT_VERSION`. Тот же номер повторно Sparkle не
   покажет: у кого плохая версия уже стоит, тот увидит обновление только на
   номере выше.

Чего делать нельзя:

- **Перезаливать образ под тем же именем.** Подпись в ленте перестанет
  сходиться, и обновление отвалится у всех с сообщением про несовпадение
  EdDSA.
- **Менять `docs/appcast.xml` руками, не трогая подпись.** Подпись считается
  по файлу образа, а не по ленте, но `length` и `sparkle:edSignature` должны
  соответствовать ровно тому файлу, который лежит по ссылке.
- **Менять идентификатор приложения** — см. ниже, это отдельный способ
  сломать всё необратимо.

Если сломан сам контур обновлений (потерян ключ, разошлись ключ и сборка,
лента отдаёт 404), то дотянуться до уже установленных копий нечем. Остаётся
объявить об этом в README и в описании релиза и просить поставить заново
руками.

## Почему так, а не иначе

### Про подпись: почему не `--deep`

`scripts/build-dmg.sh` подписывает вложенный код по одному, изнутри наружу:
`Installer.xpc`, `Downloader.xpc`, `Autoupdate`, `Updater.app`, потом сам
`Sparkle.framework` и только в конце приложение. Порядок и состав взяты из
документации Sparkle.

Соблазн заменить это одной строкой с `--deep` надо гасить. Apple объявила
`--deep` для подписи устаревшим, а Sparkle просит не применять его прямо:
`Downloader.xpc` подписывается со своими entitlements, которых нет у остальных
двоичных файлов, а `--deep` накрывает всё вложенное одинаковыми опциями.
Ломается при этом не сборка и не нотаризация, а установка обновления — то есть
у первого же пользователя и на той единственной дороге, по которой ему можно
было бы доставить исправление.

Честности ради: в нынешней сборке приложение не в песочнице, и список
entitlements у `Downloader.xpc` пустой — то есть терять пока нечего, и дефект
спящий. Но замечен он будет ровно тогда, когда песочница или сам Sparkle
что-нибудь туда добавят, и замечен будет уже пользователем.

Для **проверки** `--deep` наоборот нужен: `codesign --verify --deep --strict`
обходит вложенный код. Скрипт вдобавок сверяет, что каждый вложенный компонент
подписан тем же удостоверением, что и приложение, — пропущенный остался бы с
ad-hoc подписью сборки.

### Пробные сборки: что ими можно проверить, а что нельзя

```bash
./scripts/build-dmg.sh
```

Команда собирает запускаемый Debug-probe `Wai Dictation Dev` с отдельным
bundle id `is.waiwai.dictation.dev` и проверяемой ad-hoc-подписью. Он годится
для CI и локального smoke, но не портит production-разрешения и не
создаёт неразличимые строки Accessibility.

Проверка production identity, Developer ID, Hardened Runtime, Gatekeeper и
нотаризация идёт только через `./scripts/build-installable-beta.sh` или
полный `./scripts/release.sh`. Installable beta по умолчанию тоже требует
чистое git-дерево. Явный `ALLOW_DIRTY_BETA=1` разрешён только для
локального QA незакоммиченного кода, не для публичной раздачи. Такой билд
получает уникальный UTC build number; его можно задать явно через
`BUILD_NUMBER_OVERRIDE`.

### Идентификатор приложения менять нельзя

Release всегда требует `is.waiwai.dictation`, Debug-probe —
`is.waiwai.dictation.dev`. Скрипт останавливается при любом расхождении.
Production-идентификатор передаётся в `codesign --identifier` явно.

Причина простая: универсальный доступ выдаётся системой конкретному
идентификатору. Смените его — и после обновления человек обнаружит, что
горячая клавиша молчит и текст не вставляется, а причина ниоткуда не видна.

### Почему автопроверка выключена

`SUEnableAutomaticChecks: false` в `project.yml` — не мелочь и не оплошность.
Без этого ключа Sparkle на втором запуске сам показывает окно «проверять
обновления автоматически?» и по умолчанию включает проверки. Приложение,
которое обещает «сеть только по вашей команде», ходило бы в сеть само.

Поэтому:

- `SUEnableAutomaticChecks: false` — мы ответили за пользователя «нет»;
- `SUSendProfileInfo: false` — отчёт о железе и системе не отправляется;
- `SUAllowsAutomaticUpdates: false` — фоновой установки нет даже как опции.

Все три строки проверяет `scripts/check-network-surface.sh` на каждой сборке.
Если решите что-то из этого поменять — сначала поменяйте обещание в
`README.md` и в онбординге, а не наоборот.
